# AI 티가 나지 않는 디자인을 위한 공통 규칙

이 문서는 특정 시안에 대한 주의 메모가 아니라 **이 MCP를 참조하는 모든 프로젝트에서 항상 적용하는 디자인 규칙**입니다. 신규·기존 프로젝트, 웹·앱, 화면·컴포넌트·그래픽·모션에 공통으로 적용합니다. 패턴·예제·적용 계획보다 먼저 읽고, 디자인 요소의 선택·배치·구현·수정·검수 내내 기준으로 사용합니다. 한 번 읽고 끝내는 참고 자료가 아닙니다.

목표는 **AI가 습관적으로 조합한 듯한 상투적 표현을 피하고, 실제 내용과 목적에 맞는 시각적 완성도를 만드는 것**입니다. 제작 주체를 판별하거나 인간이 만들었다고 위장하기 위한 문서가 아닙니다.

## 0. 모든 프로젝트에 적용하는 원칙

- **내용이 형태를 결정합니다.** 템플릿을 먼저 만들고 문구·이미지·항목 수를 억지로 끼워 맞추지 않습니다.
- **요소마다 역할이 있어야 합니다.** “세련돼 보여서”, “빈 곳을 채우려고”만으로 박스·선·화살표·아이콘·효과를 추가하지 않습니다.
- **강조는 편집으로 만듭니다.** 정보의 중요도에 따라 크기·무게·간격·위치·대비를 조절하며 장식 하나로 위계를 대신하지 않습니다.
- **새로운 상투성으로 바꾸지 않습니다.** 카드 제거 후 거대 타이포·검정 배경·비대칭을 무조건 넣는 것도 같은 실패입니다.
- **모든 디자인 변경에 다시 적용합니다.** 초기 화면뿐 아니라 추가 화면, 재사용 컴포넌트, 반응형 변형, 오류·빈 상태, 모션에도 같은 규칙으로 검수합니다.
- **예제보다 이 규칙을 우선합니다.** MCP 예제나 레퍼런스에 표현이 있다는 사실은 사용 근거가 아닙니다. 명시적인 사용자 요구나 기존 승인 기준과 충돌하면 이를 알리고 범위를 확인하며, 기능·접근성은 보존합니다.

## 1. 핵심 금지 패턴

아래의 장식적 사용은 모든 프로젝트에서 금지합니다. 프로젝트 종류나 선택한 시각 스타일이 예외 사유가 되지 않습니다. 기존 프로젝트에서는 작업 범위의 디자인 요소에 적용하되, 관련 없는 화면까지 승인 없이 일괄 수정하지 않습니다.

| 피할 패턴 | 문제 | 대안 |
| --- | --- | --- |
| 박스형 디자인 | 모든 제목·설명·이미지를 카드나 테두리 상자에 가둬 내용과 무관한 구획을 반복함 | 타이포 위계·여백·정렬·이미지 크기로 묶고 구분함. 실제 독립 조작·선택·입력에 필요한 컨테이너만 사용 |
| 박스 좌측의 세로줄 포인트 | 왼쪽 색 막대 하나로 강조를 대신하는 상투적인 콜아웃·카드 구성 | 제목의 무게·정보 순서·간격·필요한 면 대비로 강조. 의미 있는 상태 표시는 색만으로 전달하지 않음 |
| 장식용 대각선 화살표 | 제목 옆이나 카드 구석의 화살표를 감각적인 장식처럼 반복 | 필요 없으면 제거. 링크나 이동에는 실제 동작에 맞는 라벨과 프로젝트의 기능 아이콘을 사용 |

기능상 필요한 입력 테두리·선택 상태·외부 링크 표시·도표의 방향 표시는 장식과 구별합니다. 금지 패턴을 피한다는 이유로 조작 가능성, 상태 구분, 읽기 순서와 접근성을 없애지 않습니다.

## 2. 상투적 표현을 피하는 요소별 규칙

아래 항목도 모든 프로젝트의 선택·검수 기준입니다. 요소 자체를 일괄 금지하는 것이 아니라 **내용과 관계없이 묶음으로 적용하는 사용 방식**을 금지합니다. 사용할 경우 실제 콘텐츠·기능·승인된 시각 방향에 따른 이유가 있어야 합니다.

| 표현 | 경계할 사용 | 더 나은 판단 |
| --- | --- | --- |
| 같은 크기의 카드 세 칸 | 모든 내용을 억지로 세 가지 특징으로 나눔 | 실제 항목 수·중요도·내용 길이에 맞게 편집 |
| 의미 없는 영문 슬로건 | 구체적인 설명 대신 “Beyond the ordinary”, “Crafted for you” 같은 문구 | 사용자의 언어로 대상·가치·행동을 구체적으로 설명 |
| 영문 소제목·작은 대문자·넓은 자간 | 한국어 화면에 맥락 없는 영어 장식을 반복 | 언어와 서체에 맞는 조판. 작은 글씨로 정보를 숨기지 않음 |
| 별·스파클·배지·번호·칩 | 빈 공간을 채우려 의미 없는 표식을 추가 | 실제 분류·순서·상태가 있을 때만 사용 |
| 그라데이션·글로우·유리 효과 | 주제와 관계없이 세련됨의 기본값으로 적용 | 제품 분위기와 시각 위계에 필요한 효과만 선택 |
| 둥근 카드·알약 버튼의 전면 적용 | 제목·태그·탐색·행동이 모두 같은 모양 | 요소의 역할과 기존 디자인 시스템에 맞게 구별 |
| 템플릿형 히어로 | 큰 제목·흐린 설명·버튼 두 개·우측 목업 구도를 무조건 반복 | 실제 화면 목적과 콘텐츠를 먼저 정하고 구도 선택 |
| 근거 없는 숫자·후기·로고 나열 | 신뢰감을 꾸미려고 실적이나 증언을 만들어냄 | 확인된 자료만 사용. 가상 예시는 명확히 표시 |
| 의미 없는 아이콘과 이모지 | 각 문단에 기계적으로 같은 크기 아이콘을 붙임 | 탐색이나 이해를 돕는 경우에만 사용 |
| 습관적인 비대칭·크롭·겹침 | 카드 대신 에디토리얼 장식을 억지로 적용 | 내용에 맞는 대비와 리듬을 만들되 읽기·조작을 보존 |
| 과잉 모션 | 모든 요소에 등장·부유·호버·스크롤 효과를 적용 | 상태 변화와 시선 안내에 필요한 모션만 사용. 동작 줄이기 지원 |

미니멀·검정·명조·에디토리얼도 자동 정답이 아닙니다. 다른 상투적 스타일로 갈아끼우지 말고, 실제 내용 때문에 형태가 결정되게 합니다.

## 디자인 예시를 받으면 색감·레이아웃·폰트를 분리해서 먼저 분석

사용자의 명시적 작업 규칙이다. 디자인 예시·이미지·스크린샷·URL·HTML을 받으면 **구현이나 새 시안 제안보다 색감·레이아웃·폰트를 분리해서 먼저 분석**하고, 아래 세 제목으로 바로 시작한다. 사용자가 “색감만”처럼 범위를 지정하면 요청한 항목만 분석한다. 이 MCP를 사용하는 모든 프로젝트에 적용한다.

### 사용자가 제공하는 예시는 선호 레퍼런스

2026-11-18 사용자는 앞으로 직접 제공하는 디자인 예시가 마음에 든다는 뜻이라고 명시했다. **사용자가 제공하는 예시는 마음에 드는 디자인으로 받아들인다.** 다시 마음에 드는지 묻거나 선호 여부를 미확인으로 취급하지 않는다. 비선호·비교용 등 다른 목적을 명시하면 그 설명을 우선한다. AI가 임의로 고른 예시나 만든 재현 시안까지 사용자 승인으로 확대하지 않는다.

### 색감 분석

배경색·본문색·강조색, 배색 관계, 명도·채도·대비, 색의 면적 비율과 분위기를 분석한다. 화면 구조에 대한 판단과 섞지 않는다. 이미지에서 추정한 HEX·수치는 추정임을 표시한다.

### 레이아웃 분석

색과 별개로 화면의 틀·구획·그리드·비율·정렬·여백·겹침·읽는 순서를 분석한다. 글자의 구성·크기·굵기·행간·자간·줄바꿈·배치와 이미지 위치·크롭도 포함한다. 정확한 서체·치수·반응형 동작을 확인할 수 없으면 추정과 관찰을 구분한다.

### 폰트 분석

서체명·패밀리·스타일·웨이트, 제목/본문/보조 정보의 역할, 한글·영문 조합과 대체 서체를 분석한다. 소스가 있으면 font-family·@font-face·로드 상태와 가능한 범위에서 실제 렌더링 서체를 확인한다. CSS 선언만으로 실제 적용 서체를 확정하지 않으며 fallback 여부를 구분한다. 이미지뿐이면 확인 가능한 조형적 특징과 추정 후보·유사 대안을 나누고 정확한 폰트명을 단정하지 않는다. 재사용 시 확인 가능한 출처·라이선스와 미확인 사항도 기록한다.

세 축을 나누는 목적은 선호를 유보하는 것이 아니라 마음에 드는 디자인의 구성과 재사용 원리를 추출하는 것이다. 전체 디자인 선호는 확인된 사실로 기록하고, 특정 요소를 좋아하는 정확한 이유나 여러 예시의 공통 경향을 AI가 추론한 경우에는 해석으로 구분한다. 요소별 분석과 반복되는 특징을 축적하고, 이후 디자인에서는 관련 선호 레퍼런스를 먼저 찾아 목적에 맞게 반영하며 어떤 요소를 활용했는지 설명한다. 사용자가 특정 요소만 좋다고 하면 그 범위를 따른다. 한 예시의 모든 요소를 모든 프로젝트의 고정 규칙으로 만들거나 그대로 복제하지 않는다. 열람 가능한 예시가 있으면 불필요한 취향 질문으로 분석을 미루지 않는다. 자료에 접근할 수 없을 때만 필요한 자료를 요청한다. 구현까지 요청받았으면 분석 후 이어서 구현하고, 분석만 요청받았으면 임의로 구현하지 않는다.

### 분석 결과 축적

**저장은 별도 요청 없이 분석의 기본 단계다.** “색감만 분석해”도 해당 예시를 `analysisScope: ["color"]`로 등록해 색감 누적 로그에 남긴다. 분석하지 않은 레이아웃·폰트는 비워 넣지 말고 아예 제외한다. 사용자가 저장하지 말라고 명시한 경우에는 저장하지 않는다.

새 예시의 분석을 대화에만 남기지 않고 예시별 JSON으로 보존한다. `design://analysis-template`, `design://analysis-schema`, `design://analysis-workflow`를 참고해 요청 범위의 관찰·근거·확인/추정/미확인·재사용 원칙을 기록한다. 연결된 AI가 파일·터미널 도구로 DESIGN 소스 저장소에 등록하고 문서 생성·검증에 성공했을 때만 저장 완료라고 말한다. MCP 자체는 읽기 전용이며 새 기록 조회에는 서버 재시작이 필요하다. 저장소에 접근할 수 없으면 미저장임을 명시하고 등록 가능한 JSON을 제공한다. 기록과 보고서는 npm 배포 대상이므로 개인 자산·기밀 원문·인증 URL을 넣지 않는다. 저장된 결과는 `search_design_analyses`와 `get_design_analysis`로 조회하며, 초안과 실제 분석·서체 선언과 실제 렌더링을 구분한다.

기본 세 축 외에 자료에 해당하는 글자 배치·인물/피사체 구도·조명·모션·질감·상호작용은 `elements`에 분리해 근거와 함께 기록한다. 실제 광원·소스·움직임·조작 상태를 관찰할 수 없으면 추정과 미확인을 구분한다. 사용자 선호 분석을 한 번 등록하면 예시별 보고서와 해당 요소별 로그가 JSON에서 자동 생성된다. `design://analyses`의 `logs` 또는 `design://analysis-logs/{axis}`에서 찾으며 문서에 직접 이중 기록하지 않는다.

`design://analysis-scope`를 참고해 관찰마다 관련된 세부 `focus`를 붙인다. 글자 위치와 줄바꿈, 빛 방향과 국소 명암처럼 다른 사실을 한 문장에 묶지 않는다. 자료에 해당하는 세부 항목만 기록하고, 확인되지 않는 특성을 분류표를 채우려고 만들어내지 않는다.

### 모호한 요청을 디자인 결정으로 바꾸기

목표는 레퍼런스를 많이 붙이는 것이 아니라 사용자에게 맞는 결정을 내리는 것이다. `get_design_preferences` 또는 `design://design-preferences`와 `search_design_analyses(scope: "preferred")`로 관련 근거부터 찾는다. 지금 요청·프로젝트 목적·기능·접근성에 맞는 명시 피드백, 독립 예시의 반복 패턴, 단일 예시의 가설 순서로 참고한다. 전체 디자인 선호와 개별 요소의 선호를 혼동하지 않는다.

분위기를 색의 역할, 편집 밀도, 시선의 순서, 움직임의 강도 등 구체적인 선택으로 옮긴다. 무엇을 보존하고 무엇은 바꿀 수 있는지, 다른 요소와 어디서 충돌하는지, 어떤 조건에서는 적용하지 않는지 적고 실제 화면에서 검수한다. 결정에 영향을 주는 관찰과 피드백은 같은 JSON의 `preferenceSignals`에 근거와 함께 적는다. 사용자가 제외한 시안은 분석과 취향 근거에서 빼며, 시안 전체의 거절을 개별 요소의 비선호로 확대하지 않는다.

## 3. 적용 순서

1. 프로젝트마다 이 문서를 먼저 읽고 적용 기준으로 삼습니다. 사용자의 요청, 기존 프로젝트의 승인된 디자인과 충돌하는 부분을 확인합니다.
2. 실제 콘텐츠·핵심 행동·화면 목적·보존할 기능을 조사합니다. 기존 디자인을 무단으로 전면 교체하지 않습니다.
3. 현재 요청에 맞는 취향 근거를 확인한 뒤 필요한 구현 패턴과 예제만 검색합니다. 예제에 금지 패턴이 있어도 사용 허가로 해석하지 말고 원리만 선택적으로 참고합니다.
4. 주요 요소의 배치·강조·장식이 왜 필요한지 내용이나 기능으로 설명할 수 있게 설계합니다.
5. 실제 렌더링을 확인합니다. 코드가 빌드됐다는 이유만으로 시각적 완성도가 검증됐다고 보고하지 않습니다.
6. 화면이나 요소를 추가·수정할 때마다 아래 체크리스트로 다시 검수합니다. 위반 요소는 제거하거나 내용·기능에 맞게 재설계한 뒤 완료 여부를 판단합니다.

## 4. 완료 전 체크리스트

- 내용을 전부 박스에 가두거나 좌측 세로줄로 강조를 대신하지 않았는가?
- 의미 없는 대각선 화살표·영문 카피·배지·아이콘을 넣지 않았는가?
- 실제 정보 위계와 다른 동일 크기 카드·기계적인 반복을 만들지 않았는가?
- 색·서체·여백·구도·효과의 선택을 화면 목적과 연결해 설명할 수 있는가?
- 실제 문구와 데이터로 좁은 화면·큰 글씨·긴 내용·오류·빈 상태를 확인했는가?
- 키보드·터치·대비·상태 식별·동작 줄이기를 보존했는가?
