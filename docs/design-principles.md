# 내 디자인 원칙

사용자가 직접 밝힌 디자인 원칙을 정리한 문서다. 사용자가 제공하는 예시는 마음에 드는 디자인이라는 명시적 기준에 따라 선호 레퍼런스로 축적한다. AI가 제안한 일반론이나 추론한 선호 이유를 사용자가 직접 확정한 원칙과 혼동하지 않는다.

## 1. AI 티가 나지 않는 디자인

디자인에서 AI 티가 나지 않도록 한다. 이를 일회성 주의사항이 아니라 모든 프로젝트의 디자인 요소에 적용하는 규칙으로 삼는다.

## 2. 피해야 할 표현

### 박스형 디자인

내용을 박스에 가두는 식의 디자인을 피한다. 박스를 반복해서 배치하는 것을 디자인의 기본 해법으로 삼지 않는다.

### 좌측 세로줄 포인트

박스나 내용 왼쪽에 세로줄을 붙여 포인트를 주는 표현을 사용하지 않는다.

### 장식용 대각선 화살표

제목 옆이나 카드 구석 등에 장식으로 붙이는 대각선 화살표를 사용하지 않는다.

## 3. 모든 프로젝트에서 적용

어떤 프로젝트를 디자인하든 이 원칙을 참조하고 실제 디자인 요소에 적용한다. 특정 예제나 한 화면에만 적용하는 기준으로 취급하지 않는다.

이 MCP를 다른 프로젝트에서 참조할 때도 디자인 규칙을 가장 먼저 읽고 참고하도록 한다.

## 4. 아직 정하지 않은 기준

사용자가 제공하는 예시는 선호 레퍼런스다. 그 예시의 색상·배색·채도·명도·색의 면적 비율, 서체·여백·구도·질감을 분석하고, 반복되는 특징을 취향의 근거로 축적한다. 전체 디자인 선호와 AI가 추론한 요소별 선호 이유는 구분한다.

한 예시의 스타일을 모든 프로젝트에 적용할 유일한 고정 취향으로 만들지는 않는다. 이후 디자인에서는 관련 선호 레퍼런스를 먼저 찾아 목적에 맞게 반영하고, 어떤 색감·구도·서체 특성을 활용했는지 설명한다. 추가 설명·예외·수정 요청은 기존 해석보다 우선한다.

## 5. 시안의 최소 완성도 기준

2026-11-11 사용자는 아래 네 시안을 직접 지정하며, 이 정도 수준이 아니면 만족할 수 없다고 밝혔다. 이후 시안의 최소 완성도 기준으로 참조한다.

- [Forma / 건축](../designs/references/reference-house.html)
- [Fold / 편집](../designs/references/reference-exhibition.html)
- [후반전 / 스포츠](../designs/references/reference-sport.html)
- [담 / 조명](../designs/references/reference-object.html)

단순히 동작하거나 반응형 검사를 통과하는 것과 시각적 완성도를 구분한다. 새 시안은 이 네 화면의 실제 렌더링과 비교해 검수한다. 네 시안의 특정 배색·서체·소재를 모두 고정 취향으로 간주하거나 큰 글자만 넣으면 충족한다고 해석하지 않는다.

## 6. 디자인 예시는 색감·레이아웃·폰트를 분리해서 먼저 분석

2026-11-17 사용자는 앞으로 디자인 예시를 가져오면 **색감과 레이아웃(글자 구성·배치·틀)을 분리해서 분석부터 바로 시작**하도록 요청했고, 이어서 **예시에 사용된 폰트 분석도 추가**하도록 요청했다. 모든 프로젝트의 개인 작업 규칙과 이 MCP의 공통 지침에 적용한다.

- **색감 분석**: 배경·본문·강조색, 배색 관계, 명도·채도·대비, 색 면적과 분위기를 독립적으로 분석한다.
- **레이아웃 분석**: 색과 별개로 화면의 틀·구획·그리드·비율·정렬·여백·겹침·읽는 순서, 글자의 구성·크기·굵기·행간·자간·줄바꿈·배치, 이미지 위치·크롭을 분석한다.
- **폰트 분석**: 서체명·패밀리·스타일·웨이트, 제목/본문/보조 정보의 역할, 한글·영문 조합과 대체 서체를 분석한다. 소스의 font-family·@font-face·로드 상태와 실제 렌더링 서체의 확인 여부를 구분한다. 이미지뿐이면 특징·추정 후보·유사 대안을 구분하고 정확한 폰트명을 단정하지 않는다. 재사용할 때 출처·라이선스의 확인 여부도 기록한다.
- 구현이나 새 시안 제안보다 위 세 분석을 독립된 제목으로 먼저 제시한다. 자료를 열람할 수 있으면 불필요한 취향 질문으로 분석을 미루지 않는다.
- 이미지에서 추정한 색 코드·치수·서체·반응형 동작은 확인된 사실과 구분한다. 세 축을 나누는 것은 마음에 드는 디자인을 구성 요소별로 분석·재사용하기 위해서이며 선호 여부를 유보하기 위해서가 아니다. 사용자가 특정 요소만 좋다고 명시하면 그 범위를 따른다.
- 구현까지 요청받으면 분석 후 이어서 구현한다. 분석만 요청받은 경우 임의로 구현하지 않는다.

분석 항목의 사실 확인 수준과 사용자가 그 디자인을 좋아한다는 사실은 별개다. 예를 들어 정확한 폰트명을 모르더라도 해당 예시가 선호 레퍼런스라는 사실은 유지한다.

## 7. 분석 결과를 계속 축적

사용자는 디자인 예시 분석 결과를 문서와 MCP에서 재사용할 수 있도록 축적 가능하게 해 달라고 요청했다. 세 축을 유지한 예시별 기록에 근거·불확실성·재사용 원칙을 남기고, 새 예시마다 추가할 수 있게 한다.

작성 원본은 [예시별 JSON](../content/analyses/), 사람이 읽는 결과는 [누적 분석 보고서](./analyses/README.md)다. [등록·수정·조회 안내](./recording-analyses.md)에 따라 실제 파일을 저장·검증하고 MCP를 재시작한다. 저장하지 못했으면 미저장 상태를 명시한다. 원문 자산·민감 정보는 배포 대상 분석 기록과 분리한다.

## 8. 앞으로 제공하는 예시는 마음에 드는 디자인

2026-11-18 사용자는 **앞으로 디자인 예시를 주는 것은 마음에 든다는 뜻**이라고 명시했다. 마음에 드는지 다시 확인하지 않고, 분석 결과를 선호 레퍼런스로 저장하며 이후 디자인의 참고 기준으로 활용한다. 여러 예시의 공통 특징도 축적하되 AI의 해석과 사용자가 직접 지정한 선호를 구분한다.

비선호·비교용 등 다른 목적을 명시하면 그 설명을 우선한다. AI가 임의로 찾은 예시나 만든 재현 시안 전체를 사용자가 승인한 것으로 소급하지 않는다. 분석만 요청했으면 구현은 임의로 시작하지 않되, 선호 분석의 축적은 계속한다.

## 관련 문서

[AI 티가 나지 않는 디자인을 위한 공통 규칙](../content/design-cautions.md)은 MCP에서 먼저 전달하는 적용 문서다. 그 문서에는 AI가 제안한 추가 지침도 포함돼 있으므로, 모든 항목을 사용자가 직접 명시한 취향과 동일하게 취급하지 않는다.
